# 3. VISIÓN DEL PRODUCTO

Quiero construir una plataforma con dos grandes experiencias principales y un sistema de gestión común.

## Modo A — Arquitectura 3D interactiva

Orientado a arquitectos, diseñadores y estudios.

Un profesional puede cargar un proyecto, organizar sus modelos, renders y planos, generar experiencias visuales y compartir un enlace con sus clientes.

El visitante puede explorar la arquitectura, mirar alrededor, navegar por habitaciones y consultar detalles del proyecto.

## Modo B — Showroom inmobiliario

Orientado a desarrolladores inmobiliarios, constructoras e inmobiliarias.

El usuario puede explorar un barrio, edificio o promoción inmobiliaria desde una vista aérea 3D, seleccionar una propiedad, ver su disponibilidad, recorrerla virtualmente y solicitar información.

## Modo C — Administración y publicación

Un panel privado permite administrar múltiples proyectos, modelos 3D, panoramas, unidades comerciales, ubicaciones, escenas, usuarios, precios y consultas recibidas.

## Modo D — Procesamiento CAD/BIM e IA

Un módulo de procesamiento permite importar planos y modelos arquitectónicos y transformarlos progresivamente en recursos compatibles con la plataforma.

Debe combinar herramientas deterministas, automatización, asistencia por IA y revisión humana para los pasos que no puedan resolverse con fiabilidad.

# 4. STACK TECNOLÓGICO PROPUESTO

Investigá las versiones estables, compatibilidades y licencias antes de instalar las dependencias.

Usá este stack como referencia principal, salvo que encuentres alternativas técnicamente superiores y justifiques el cambio.

## 4.1 Frontend

- Next.js
- React
- TypeScript con modo estricto
- Tailwind CSS
- shadcn/ui
- Radix UI
- Lucide Icons
- Zustand para estado local
- TanStack Query para estado servidor
- React Hook Form
- Zod para validaciones

Implementá una interfaz moderna, modular y completamente responsive.

Separá la interfaz del visitante de las herramientas administrativas.

## 4.2 Motor 3D

Tecnologías principales:

- `three`
- `@react-three/fiber`
- `@react-three/drei`
- `@react-three/postprocessing`
- `camera-controls`
- `gsap`

Usalas según necesidad, sin incorporar librerías innecesarias.

Three.js debe manejar:

- Escenas tridimensionales.
- Geometrías.
- Modelos GLB/GLTF.
- Materiales PBR.
- Cámaras.
- Iluminación.
- Selección de objetos.
- Raycasting.
- Sombras.
- Transiciones.
- Geometría instanciada.
- Texturas.
- Niveles de detalle.

React Three Fiber debe integrar las escenas con React.

Drei debe facilitar controles, carga de modelos y utilidades del visor.

Postprocessing debe utilizarse únicamente cuando mejore visualmente la escena sin perjudicar excesivamente el rendimiento.

## 4.3 Motor de recorridos 360°

Investigá y compará:

- Marzipano
- Photo Sphere Viewer
- Pannellum
- Un visor propio basado en Three.js, si existe una justificación clara

Seleccioná preferentemente Marzipano o Photo Sphere Viewer para los recorridos panorámicos.

El motor debe admitir:

- Imágenes equirectangulares.
- Cubemaps.
- Panoramas multirresolución.
- Movimiento horizontal y vertical.
- Zoom.
- Hotspots.
- Transiciones entre escenas.
- Navegación táctil.
- Pantalla completa.
- Miniaturas.
- Plano interactivo.

No utilices un motor 3D generalista para implementar recorridos panorámicos si una librería especializada ofrece mejor rendimiento y mantenimiento.

## 4.4 Renderizado arquitectónico

Investigá e integrá, inicialmente como pipeline offline:

- Blender
- Blender Cycles
- glTF 2.0
- glTF Transform
- Meshoptimizer
- Draco cuando corresponda
- KTX2/Basis Universal
- Sharp
- FFmpeg

Investigá también opciones como Unreal Engine, Twinmotion, Enscape, D5 Render o V-Ray, pero no las introduzcas como dependencias obligatorias del MVP.

El objetivo es conseguir imágenes de alta calidad sin exigir que todos los visitantes tengan una GPU potente.

La estrategia principal debe ser híbrida:

- Three.js para interacciones 3D reales.
- Panoramas prerenderizados para interiores fotorrealistas.
- Blender u otro motor offline para crear recursos visuales.
- UI web convencional para datos y administración.

## 4.5 Backend

Stack preferido:

- Node.js LTS
- TypeScript
- Fastify
- PostgreSQL
- Drizzle ORM o Prisma
- Redis
- BullMQ
- OpenAPI

Podés utilizar NestJS si justificás que sus módulos y estructura aportan beneficios importantes.

Creá una API REST versionada con contratos tipados y validación.

## 4.6 Archivos y almacenamiento

Implementá una capa abstraída para almacenamiento compatible con S3.

Opciones:

- MinIO en desarrollo local.
- Cloudflare R2 o equivalente en producción, sujeto a costos y condiciones.
- CDN para recursos públicos.

Utilizá URLs firmadas para uploads y permisos adecuados para assets privados.

No dependas exclusivamente de una plataforma propietaria.

## 4.7 Mapas

Usá MapLibre GL JS.

Integrá:

- Ubicación geográfica del proyecto.
- Marcadores.
- Puntos de interés.
- Navegación.
- Visualización satelital cuando haya un proveedor autorizado.
- Distancias o rutas cuando exista un servicio compatible.

No utilices tiles, mapas satelitales ni APIs sin verificar sus condiciones de uso.

# 5. ARQUITECTURA DEL SISTEMA

Creá un monorepositorio administrado con pnpm workspaces.

Estructura recomendada:

`apps/showroom` — Web pública para visitantes.

`apps/admin` — Panel de administración.

`apps/api` — Backend principal.

`packages/ui` — Componentes compartidos.

`packages/domain` — Modelos y reglas de negocio.

`packages/contracts` — Esquemas y contratos API.

`packages/3d-engine` — Componentes Three.js/R3F.

`packages/tour-engine` — Adaptador del visor 360°.

`packages/assets` — Tipos y herramientas de recursos.

`workers/asset-processing` — Procesamiento de archivos.

`workers/render-processing` — Renderizado offline.

`tools/cad-importer` — Adaptadores CAD/BIM.

`docs` — Arquitectura y documentación.

`tests` — Pruebas integrales.

Separá claramente la lógica de dominio de la tecnología de renderizado.

El frontend no debe depender de detalles internos de la base de datos.

El motor 3D no debe contener lógica comercial de disponibilidad, precios o ventas.

Implementá interfaces y adaptadores para facilitar futuros cambios de tecnología.

# 6. FUNCIONALIDAD: VISOR ARQUITECTÓNICO

Esta es una de las funcionalidades más importantes del producto.

Quiero que un visitante pueda entrar a una casa y recorrerla visualmente como en los videos.

## 6.1 Navegación

El usuario debe poder:

- Girar la cámara.
- Mirar hacia arriba y abajo.
- Hacer zoom.
- Navegar con mouse.
- Navegar con touch.
- Cambiar de habitación.
- Utilizar flechas de desplazamiento.
- Seleccionar habitaciones desde un plano.
- Cambiar entre cámaras guardadas.
- Volver al punto anterior.
- Entrar en modo pantalla completa.

Implementá transiciones visualmente suaves y naturales.

## 6.2 Hotspots

Cada escena puede tener puntos interactivos.

Tipos:

- Ir a otra habitación.
- Ver información.
- Mostrar materiales.
- Abrir una fotografía.
- Mostrar una descripción.
- Abrir un plano.
- Ir a una vista exterior.

Cada hotspot debe guardar:

- Identificador.
- Escena de origen.
- Tipo.
- Posición angular o espacial.
- Texto.
- Icono.
- Destino.
- Comportamiento.
- Estado de publicación.

Los hotspots deben ser administrables sin modificar código.

## 6.3 Plano interactivo

Implementá una funcionalidad similar al modal "Ir a un punto" de los videos.

Mostrar un plano de la propiedad con puntos seleccionables.

Al hacer clic en un ambiente:

1. Cerrar o minimizar el plano.
2. Cargar la escena correspondiente.
3. Orientar la cámara a un ángulo inicial.
4. Actualizar el punto activo.
5. Mantener sincronización con los hotspots.

Utilizá SVG con coordenadas normalizadas para que el plano sea responsive.

## 6.4 Calidad del render

Quiero una estética visual de arquitectura premium.

Priorizá:

- Materiales físicamente plausibles.
- Iluminación natural.
- Texturas de alta resolución.
- Reflejos coherentes.
- Buena exposición.
- Sombras suaves.
- Interiores realistas.
- Transiciones limpias.

No confundas calidad fotorrealista con renderizado calculado en tiempo real.

Para interiores complejos, preferí panoramas de alta calidad generados offline.

# 7. FUNCIONALIDAD: MASTERPLAN 3D INTERACTIVO

Construí un visor tridimensional para explorar un desarrollo inmobiliario.

El usuario debe ver:

- Terreno.
- Calles.
- Vegetación.
- Edificios o villas.
- Unidades comercializables.
- Posiciones geográficas relativas.
- Elementos arquitectónicos.
- Etiquetas de identificación.

## 7.1 Controles

Implementá:

- Rotación orbital.
- Zoom.
- Pan cuando corresponda.
- Vista cenital.
- Vista isométrica.
- Restablecer cámara.
- Selección de unidades.
- Animación de enfoque.
- Cambio de perspectiva.

La cámara nunca debe atravesar accidentalmente la geometría del terreno.

Limitá ángulos, distancias y movimientos según la escena.

## 7.2 Selección de viviendas

Cada vivienda debe poder seleccionarse mediante clic o toque.

Utilizá raycasting o picking 3D real.

Al seleccionar una vivienda:

- Resaltar su geometría.
- Mostrar su nombre.
- Consultar su información.
- Mostrar precio.
- Mostrar disponibilidad.
- Mostrar superficie.
- Mostrar dormitorios y baños.
- Permitir abrir su ficha.
- Permitir iniciar el recorrido virtual.

No simules la selección utilizando botones colocados sobre una imagen fija si existe una geometría real.

## 7.3 Colores comerciales

Crear estados configurables:

- Disponible.
- Reservada.
- Vendida.
- No publicada.

Utilizar colores y estilos visuales consistentes.

Los colores deben sincronizarse con los datos reales del backend.

## 7.4 Relación entre modelo y datos

Cada modelo GLB puede contener muchos objetos.

Implementá un mecanismo `UnitMeshMapping` para vincular una unidad comercial a uno o varios nodos del modelo.

Ejemplo conceptual:

- Unit ID: `villa-06`
- Meshes: `Villa_06`, `Villa_06_Roof`, `Villa_06_Garden`
- Estado: `AVAILABLE`
- Precio: definido en la base de datos

No guardes el precio directamente dentro de los archivos GLB como única fuente de verdad.

# 10. FUNCIONALIDAD: IMPORTACIÓN CAD/BIM

Quiero aproximarme a la experiencia promocionada en el primer video: pasar de planos a una experiencia 3D.

Pero debe implementarse con rigor técnico.

## 10.1 Formatos

Diseñar adaptadores para:

- DWG.
- DXF.
- IFC.
- GLB.
- GLTF.
- OBJ.
- FBX, si hay herramientas compatibles.
- SVG.
- Imágenes de planos.
- PDF de planos, en una fase posterior.

Priorizar inicialmente GLB y panoramas porque permiten publicar experiencias reales inmediatamente.

Después incorporar IFC y DXF.

DWG requiere una solución de conversión legalmente utilizable.

## 10.2 Proceso de importación

Diseñar este flujo:

1. Usuario crea proyecto.
2. Sube archivo.
3. Sistema valida formato.
4. Detecta metadatos.
5. Identifica unidades y escala cuando sea posible.
6. Almacena original.
7. Crea trabajo de procesamiento.
8. Extrae geometría.
9. Genera previsualización.
10. Permite revisión y corrección.
11. Exporta modelo optimizado.
12. Publica en el showroom.

Cada trabajo debe tener estado:

- Pending.
- Processing.
- Requires Review.
- Completed.
- Failed.

Registrar errores y permitir reintentos seguros.

## 10.3 Reconstrucción de planos 2D

Investigar una implementación gradual para reconocer:

- Paredes.
- Habitaciones.
- Puertas.
- Ventanas.
- Columnas.
- Escaleras.
- Aberturas.
- Dimensiones.
- Capas CAD.

Utilizar parsers CAD, geometría computacional e IA cuando sea apropiado.

Permitir que el administrador corrija manualmente el reconocimiento.

A partir de geometría validada, investigar extrusión de paredes, colocación de aberturas y exportación a GLB.

No asumir que cualquier DWG puede transformarse automáticamente en una casa fotorrealista.

# 18. RENDIMIENTO

El rendimiento es prioritario porque los recursos 3D pueden ser pesados.

Implementar:

- Lazy loading.
- Suspense y fallbacks adecuados.
- Descarga progresiva.
- Prefetch de escenas vecinas.
- Texturas comprimidas.
- LOD.
- Frustum culling.
- Geometría instanciada cuando sea útil.
- Resource cleanup.
- Cancelación de solicitudes obsoletas.
- Límites de DPR.
- Modos gráficos adaptativos.
- Optimización mobile.
- Manejo de context loss de WebGL.

Medir:

- FPS.
- Uso de memoria.
- Tamaño inicial descargado.
- Tiempo de carga de escena.
- Tiempo hasta primera interacción.
- Duración de transiciones.
- Cantidad de draw calls.
- Peso de modelos y texturas.

Usar presupuestos iniciales como objetivos de ingeniería, no como garantías universales.

Priorizar experiencia fluida sobre efectos gráficos innecesarios.
